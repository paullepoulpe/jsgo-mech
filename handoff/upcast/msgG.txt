j2go + runtime: typed sets and maps compared by equals and hashCode (Set<Var>, Map<Property.Key, X>, keys that are interfaces or library classes)

Rule "typed collections", seventh slice: the elements of a set and the keys of a map may be
of any class or interface without type arguments (not Object, Float or Double). Until now
they had to be of a type whose Go == is Java's equals (a String, an enum, a class of the
program without equals of its own, a boxed primitive); such a collection still compares with
== through a Go map. For every other type (a class with its own equals or hashCode, in itself,
a superclass or a subclass; an interface; a library class: Ctx.byEquals) the typed set or map
finds an element exactly as java.util.HashMap does: by the hash code the element had when it
was added, then by identity or equals(). The conversion of such a type says so (tce_p_Var:
tconv_.byEquals), and the collection keeps the hash codes beside its keys (teq_, rt_tset.go:
a scan of the hash codes while it is small, then chains of positions per hash code, as the
erased table has). hashCode and equals are called on the boxes (objhash_, objequals_: null is
a key with hash code 0), in the order and number HashMap calls them for a table without
collisions of unequal hash codes: hashCode once per operation, equals only on a key of the
same hash code that is not the same object. J2GO_COLLS_NOEQUALS=1 is the previous rule.
