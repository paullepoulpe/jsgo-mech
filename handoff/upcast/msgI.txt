j2go: typed collections in the parameters and results of groups of overriding methods

Rule "typed collections", ninth slice. Until now a parameter or a result could be a typed
collection only in a method whose signature is its own (a constructor, a static or private
method, an instance method that overrides nothing and that nothing overrides). Methods that
override one another have one signature in Go (Ctx.groupParams / groupReturn read the root's
declarations), so a parameter or the result of such methods is one declaration for the whole
group (Colls.groupOf, groupSlot): what enters it in any method of the group enters it, every
use in any of them is a use of it, and it is a typed collection in every method or in none
(Slot.all: the root's signature, each method's own declaration, the dispatch stubs and the
interface's method set follow from the same declarations).
A group is every method connected by "overrides" in some class of the program, anonymous and
local classes included; a method that a class inherits is connected to the interface method
that it implements in that class (KeyHolder.keys() and Sized.keys() through SizedHolder
extends KeyHolder implements Sized), since the Go struct must have the interface's method. A
group can be typed when
- all its methods are methods of the program (no library method: Iterable.iterator, a Guava
  interface), without type parameters, not of a record, an annotation or a handle class;
- the position has the same collection kind and type arguments in every method (not a type
  argument that names a Go type parameter: the methods are in different generic scopes);
- no lambda and no method reference implements the group's interface (their adapter has the
  erased signature: "of a method that a lambda implements" keeps it erased).
J2GO_COLLS_NOGROUPS=1 is the previous rule. J2GO_COLLS=1 now reports why a parameter or result
is not a candidate.
